# Сборка и проверки

[← Revit MCP](../README.md)

Требуются Windows x64, .NET 8 SDK, Node.js 24, pnpm 11.25.0 и Git. Для запуска надстройки нужен Revit 2026.

```powershell
pnpm --dir server install --frozen-lockfile
pnpm --dir server test
node --test installer/configure-mcp.test.mjs
node --test installer/source.test.mjs installer/runtime.test.mjs
node installer/check-release.mjs
dotnet run --project tests/ApprovalSettings.Tests/ApprovalSettings.Tests.csproj -c Release
./tests/updates.ps1
./build.ps1 -UseRevitNuGet
./build-installer.ps1 -UseRevitNuGet -SkipPluginBuild
```

Без `-UseRevitNuGet` используются API установленного Revit; путь задаётся через `-Revit2026Dir`. Для CI закреплены compile-only пакеты [Nice3point/revit-api](https://github.com/Nice3point/revit-api) 2026.0.4. Их DLL исключены из поставки. Lock-файлы находятся в `plugin/` и `loader/`.

`build.ps1` собирает `RevitMCP.Core.dll` и `RevitMCP.Loader.dll` с общими сборками Contracts и Updates. Выходные каталоги — `bin/Release/` соответствующих проектов. Сборка не меняет установленную надстройку или конфигурацию MCP.

`build-installer.ps1` создаёт в `dist/` EXE, архив соответствующих исходников и `SHA256SUMS.txt`. EXE содержит Node.js, зависимости MCP, загрузчик, начальную рабочую часть и .NET runtime. Упакованный сервер проверяется через MCP initialize и tools/list. Для получения лицензионных текстов Node.js и .NET нужен интернет.

Перед упаковкой зафиксируйте изменения отслеживаемых файлов. Архив исходников создаётся из коммита `HEAD`; незакоммиченные изменения останавливают упаковку, неотслеживаемые файлы в архив не попадают. Приватные инструкции, журналы, модели Revit и файлы сборки запрещены в архиве, даже если добавлены в Git. `-SkipPluginBuild` используйте только с DLL, собранными из того же коммита.

Тесты обновления загружают две разные DLL в одном процессе, проверяют смену поведения, сборку старого контекста GC, откат, восстановление после запуска, отсутствие блокировки DLL, отмену и отказ при нарушении контрольных сумм, состава архива или совместимости.

## GitHub Actions

`build.yml` выполняет тесты и сборку на Windows. Ветка `0.0.2` также получает установщик и пакет обновления. Пакет и манифест бета-канала публикуются на GitHub Pages после успешной проверки. Установщик и исходники доступны в артефакте запуска; GitHub Release не создаётся.

```powershell
./build-update.ps1 -BuildId (git rev-parse HEAD) -Sequence 1 -Channel beta
```

Команда формирует `dist/site/updates/beta/`. BuildId — SHA коммита, Sequence — номер запуска GitHub Actions. Повторный запуск того же коммита не заменяет установленный пакет. Манифест включает канал, исходную ветку и минимальную версию загрузчика. Пакет beta нельзя создать из `main`, стабильный пакет — из ветки разработки.

Стабильный канал использует `update.json` последнего опубликованного GitHub Release. Workflow `release.yml` собирает его из `main` с `-Channel stable` и прикладывает пакет обновления вместе с установщиком, исходниками и контрольными суммами. GitHub Pages используется только для beta; публикация beta не заменяет стабильный канал. Для перехода с beta на стабильную сборку той же версии номера запусков разных workflow не сравниваются. Выключение beta само по себе не понижает установленную версию.

Загрузчик с AssemblyVersion `0.0.2.1` поддерживает выбор канала и этапы прогресса. Пакеты с инструментами разработки семейств требуют `0.0.2.2` для синхронного обновления загрузчика и схем MCP; предыдущий загрузчик обновляется полным установщиком при закрытом Revit. При изменении схем MCP также требуется установить сервер из того же пакета и перезапустить MCP-клиент.

Инструменты модели и обнаружение нескольких процессов требуют загрузчик `0.0.2.4` и соответствующий MCP-сервер. Версия продукта остаётся `0.0.2`; платформа — Revit 2026.

Выгрузка RFA из проекта и вложений, а также передача `errorDetails` через загрузчик требуют `0.0.2.5`. Проверки сохранности экземпляров после загрузки: `dotnet run --project tests/FamilyReload.Tests -c Release`.

Сравнение с учётом служебной смены FamilyId и новых вложений, а также HVAC Global поставляются с загрузчиком `0.0.2.6` и соответствующим MCP-сервером. `FamilyReload.Tests` дополнительно принимает пути сохранённых MCP-ошибок после `--` для локального повтора сравнения `diagnostics.before`/`after`. Диагностические файлы проектов в репозиторий не включаются.

Контракты `expectedChanges` требуют полного пакета с загрузчиком `0.0.2.7` и соответствующим сервером. Для локального повтора намеренных изменений перед путями диагностик укажите `--expected <request.json>`; файл запроса должен содержать массив `expectedChanges`. Проверки сравнения не загружают Revit и не применяют изменения проекта.

Для интеграционной проверки используйте копию проекта Revit: загрузка, preview/apply, обновление на следующую сборку при открытом документе, повторный предпросмотр и откат. Дополнительно проверьте светлую и тёмную темы, масштабирование 100% и 150%, отсутствие активной транзакции при переключении. Автоматические тесты не заменяют проверку в Revit.

## Проверка семейств

`dotnet run --project tests/FamilyCatalog.Tests -c Release` проверяет разбор каталогов, кодировки, точный выбор строк и ошибки формата. Тесты сервера проверяют схемы и согласованность диспетчера. Эти проверки не исполняют Revit API.

После установки соответствующей сборки можно выполнить `node tests/family-revit.mjs <RFT> <RTE> <новая_папка>`. Нужны шаблон механического оборудования без хоста и MEP-шаблон проекта с круглыми воздуховодами. Проверка создаёт два тестовых RFA, проверяет формулы, каталог, контроль входных файлов и четыре HVAC-соединения; активный проект не изменяет. Дополнительные preview проверяют создание и редактирование Global после сохранения/повторного открытия, сохранность ID существующих коннекторов, размеров, координат и привязок. При выключенном автоподтверждении сохранение подтверждается в Revit. Успех подтверждается только итоговым `passed: true`; CI не запускает Revit и не подтверждает этот сценарий.

## Проверка инструментов модели

`node tests/model-revit.mjs <fixture.json>` выполняет проверки в открытом изолированном тестовом проекте. Конфигурация содержит абсолютный `projectPath`, явный `processId`, `elementIds` для чтения параметров и `previews` — массив объектов `{ "tool": "preview_…", "arguments": { … } }`.

Сценарий отказывается работать, если путь открытого проекта не совпал. Он проверяет каталоги, страницы параметров, результаты выбранных предпросмотров и сохранение количеств элементов после отката. Команды применения, сохранения, экспорта и управления интерфейсом не принимаются. Проверки применения, геометрии соединений и файлов экспорта выполняются отдельно на тестовых моделях; успешные тесты схем и сборка DLL не подтверждают их работу в Revit.

`node tests/family-export-revit.mjs <fixture.json>` проверяет выгрузку на изолированном проекте с подключённым семейством и вложением. Конфигурация: `processId`, абсолютные `projectPath` и новая `outputDirectory`, `familyId`, точное `nestedFamilyName`. Сценарий сохраняет два тестовых RFA, проверяет обратную загрузку через preview с `preserve`/`overwrite`, запрет перезаписи, SHA-256 исходника и отклонение изменённого источника. Путь открытого проекта должен совпасть; сохранение RFA подтверждается в Revit. Рабочая модель не применяется и не сохраняется. CI не запускает этот нативный сценарий.
